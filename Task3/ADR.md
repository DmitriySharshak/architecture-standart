### <a name="_qmphm5d6rvi3"></a>**Решение**

[Диаграмма контекста](out/C4_Context.png)\n
[Диаграмма контейнеров](out/C4_Container.png)

Логика принятия решений и выбора технологий следущая:
1. Идем по пути гибридной архитектуры. Строим новые цифровые сервисы рядом со старыми системами, соединяя их через анти-коррупционный слой (API-адаптеры, очереди). 
2. Делаем упор на асинхронное взаимодействие через брокер сообщений. Можно было выбрать Rabbit из-за его совместимости с решением написанным .NET Framework 4.5, но выбрали Kafka как отраслевой стандарт для потоковой обработки данных
3. Создан отдельный API-адаптер АБС на Java Spring Boot, т.к. у команды АБС есть экспертиза. Он выступает единственной точкой входа для записи в АБС из внешнего мира.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Прямая интеграция ИБ с АБС через её БД. Решение может привести к большой нагрузке на Oracle 
2. Использование RabbitMQ вместо Apache Kafka. Хотя Kafka мощнее и перспективнее, она сложнее в освоении и эксплуатации
3. Провести полный рефакторинг ИБ и пойти в микросервисы, но это не реалистично так как с гибридным решением быстре можно получить ценность, которая требуется

**Недостатки, ограничения, риски**
1. Усложнелась архитектура. Появилось много новых компонентов 
2. Асинхронная модель  взаимодействия добавляет в процесс задержки между подачей заявки и её появлением в АБС.
